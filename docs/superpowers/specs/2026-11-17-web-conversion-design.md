# 웹 전환 설계 (설치형 → 웹, PC·태블릿)

- 작성: 2026-11-17
- 상위 설계: [2026-11-13-production-react-design.md](2026-11-13-production-react-design.md). 이 문서는 그중 "현장 PC 전체화면 설치형(Electron)" 부분만 바꾼다.

## 왜

회사 결정으로 설치형 프로그램 대신 웹으로 전환한다(2026-11-17, 사용자 전달). 현장 PC와 태블릿 모두에서 브라우저로 접속해 쓴다.

## 목표

- 현장 PC(크롬/엣지)와 태블릿 브라우저에서 주소 하나로 접속해 지금 화면을 그대로 쓴다.
- 서버 프로그램(Spring Boot) 하나가 화면 파일과 데이터를 함께 내보낸다. 현장 기기에 설치하는 것은 없다.
- 오른쪽 위 _ 버튼은 "전체화면 해제"로 동작한다.

## 하지 않는 것

- 태블릿 전용 배치. 태블릿은 **가로로** 쓰고, PC 화면(1920 기준)을 그대로 줄여서 보여 준다(사용자 결정). 세로 방향은 따로 대응하지 않는다.
- 화면 배치·동작·저장 로직 변경. 원본과 같게 유지한다는 원칙은 그대로다.
- 서버 설치·운영(서버 PC, 포트, 자동 시작, HTTPS)은 IT 담당자 몫. 이 작업은 "서버 프로그램 파일 하나로 실행 가능"까지.
- 인쇄(라벨/리포트)는 지금처럼 보류.

## 접근 방식

| 방식 | 장점 | 단점 |
|---|---|---|
| **1. Spring Boot 가 화면까지 함께 내보냄 (선택)** | 주소 하나, CORS 설정 불필요, 배포 파일 하나 | 화면만 고쳐도 서버 프로그램 재배포 |
| 2. 화면용 웹서버(IIS/nginx) 별도 | 화면만 따로 교체 가능 | 웹서버 설치·설정, 백엔드 연결 설정, 관리 대상 둘 |

사용자가 1번을 골랐다(2026-11-17).

## 정해진 동작

### 배포 형태
- `frontend` 빌드 결과(`dist`)를 백엔드 실행 파일(jar) 안의 정적 파일로 넣는다. 현장은 `http://서버주소:포트/` 로 접속한다.
- 화면은 주소 이동(라우터)이 없는 한 페이지라서, `/` 에서 `index.html` 만 내보내면 된다. `/api/**` 는 지금 그대로.
- 개발 중에는 지금처럼 `npm run dev`(5173, `/api` 프록시)를 쓴다.

### 전체화면과 _ 버튼 (사용자 결정)
- 로그인 버튼을 누르면(또는 비밀번호 칸 Enter) 검증·요청 **전에** 브라우저 전체화면으로 들어간다. 브라우저는 누름 직후 잠깐만 전체화면을 허용하므로, 응답을 기다렸다 들어가면 느릴 때 막힌다(계획 단계에서 변경, 로그인 실패여도 전체화면만 될 뿐 무해).
- _ 버튼: 전체화면이면 해제한다. PC에서는 일반 브라우저 창이 되어 작업표시줄이 보이고 다른 프로그램으로 넘어갈 수 있다(최소화와 비슷한 효과). 로그인·메인메뉴·생산실적 화면의 _ 모두 같다.
- 브라우저가 전체화면 기능을 지원하지 않으면(아이패드 Safari 등) _ 버튼을 숨긴다.
- 키오스크 모드 바로가기는 쓰지 않는다(키오스크에서는 전체화면을 풀 수 없어 _ 가 동작하지 않음).

### X 버튼
- 생산실적 X(메인메뉴로), 메인메뉴 X(로그아웃 확인 → 로그인 화면): 지금 그대로.
- 로그인 화면 X(원본: "프로그램을 종료하시겠습니까?" → 종료): 브라우저는 스크립트가 창을 닫는 것을 막으므로 **숨긴다**. — *내 판단*

### 화면 키보드
- 태블릿: 입력 칸을 누르면 기기 키보드가 자동으로 뜬다. 작업 없음.
- 터치 PC: Windows 설정 "키보드가 연결되지 않았을 때 터치 키보드 표시"(Win11, 설정 > 시간 및 언어 > 입력 > 터치 키보드)를 켠다. 설정 방법을 안내 문서에 적는다. 원본처럼 품목 검색·참고사항 두 칸에서만 뜨게 하지는 못한다.
- 설치형용 키보드 연결(`useTabTip`, `desktop.openKeyboard/closeKeyboard`)은 브라우저에서 아무 일도 하지 않으므로 이번에는 그대로 둔다. desktop 폴더와 함께 git 정리 때 지운다. — *내 판단*

### 접속정보 파일
- 운영 jar 에는 `application-local.yml`(DB 접속정보)을 넣지 않는다. 서버에서 jar 와 같은 폴더(또는 `config/`)에 둔다 — Spring Boot 가 자동으로 읽는다. (구현 중 발견, jar 를 복사·배포할 때 접속정보가 함께 퍼지는 것 방지)

### 기기별 기억값
- 마지막 공정·작업장·설비·작업자, 아이디 저장: 지금도 브라우저에서는 브라우저 저장소(localStorage)에 저장된다. 그대로 쓴다. 브라우저 기록을 지우면 사라진다는 점을 안내 문서에 적는다.

### 외부 주소(도면·작업의뢰서)
- 지금도 브라우저에서는 새 탭으로 연다. 링크를 열지 않는 결정(사용자 확인 전까지 알림만)은 그대로.

### 설치형 껍데기
- `desktop` 폴더는 더 이상 쓰지 않는다. git 시작할 때 지운다. 그 전까지 손대지 않는다.

## 문서 갱신
- CLAUDE.md "확정된 결정"의 "현장 PC에서 전체화면 설치형 프로그램" → "웹(PC·태블릿 브라우저), Spring Boot 가 화면까지 제공". 실행 방법에 운영용 빌드·실행 한 줄 추가.
- 현장 안내 문서(새로): 접속 주소, 터치 키보드 Windows 설정, 태블릿 가로 사용, 기억값이 브라우저에 저장된다는 점.

## 만드는 사람에게 맡기는 것
- 프런트 빌드 결과를 jar 에 넣는 방법(Maven 단계에서 `../frontend/dist` 를 `static` 으로 복사 등).
- 로그인·메인메뉴·생산실적 세 곳의 _ 버튼을 하나의 공통 동작으로 묶는 방법.
- 터치 동작 점검: 마우스 전용 동작(오른쪽 클릭, 마우스 올림)이 있는지 확인. 지금 코드에 더블클릭 처리는 없다.

## 확인 방법
- 운영용으로 빌드한 jar 하나를 띄우고 `http://localhost:포트/` 로 접속 → 로그인 → 전체화면 진입 → _ 로 해제 → 생산실적 조회까지(테스트 DB).
- 화면 캡쳐 없이 DOM/텍스트로 확인.

## 변경: 화면은 Vercel (2026-11-17 오후, 사용자 결정)

회사의 다른 프로젝트(S_ERP, SONGYEON_ERP)와 같은 방식으로 **화면은 Vercel, 백엔드는 따로** 둔다. 위 "접근 방식 1(Spring Boot 가 화면까지)"은 사내 서버에서 직접 띄울 때의 대안으로 남겨 둔다(`-Pweb`).

- 화면이 부를 백엔드 주소: Vercel 프로젝트 환경변수 `VITE_API_BASE_URL`(https 백엔드 주소). 값이 없으면 같은 주소(`/api/...`) — 개발 서버 프록시·jar 직접 제공용. (`frontend/src/shared/api/baseUrl.ts`)
- `frontend/vercel.json`: 모든 경로 → `index.html` (송연·S_ERP 와 같음).
- 백엔드 CORS: "모두 허용" → 설정 `pop.cors.allowed-origins`(환경변수 `POP_CORS_ALLOWED_ORIGINS`)에 있는 주소만. 기본값은 `http://localhost:*,http://127.0.0.1:*`. Vercel 주소가 생기면 여기에 추가한다(코드 수정 없음).
- 조건: 백엔드는 **https 주소**가 있어야 하고(https 화면이 http API 를 부르면 브라우저가 막음), 회사 MSSQL 에 닿는 곳이어야 한다. 위치는 담당자 확인 필요.
- 순서: 코드 준비 → GitHub 올림 → Vercel 에서 저장소 연결(Root Directory `frontend`) → Vercel 주소를 백엔드 허용 목록에, 백엔드 주소를 Vercel `VITE_API_BASE_URL` 에.
