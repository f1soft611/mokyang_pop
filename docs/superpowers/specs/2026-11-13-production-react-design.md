## 1. 목적

현장 PC에서 쓰는 WPF POP 프로그램(iPlusPOP)의 생산실적관리 화면을 React 기반으로 옮긴다. 현장 작업자에게는 **바뀐 게 없어 보여야 한다.** 배치, 글자, 색, 버튼 위치, 알림 문구, 누르는 순서, 저장되는 데이터가 모두 원본과 같아야 한다.

바꾸는 이유는 기술 기반이다. 원본은 PC마다 DB에 직접 붙고, SQL을 문자열로 이어 붙이며, DB 비밀번호를 설정 파일에 평문으로 둔다.

## 2. 목표 / 비목표 / 실패 기준

**목표**
- 로그인 → 메인메뉴 → 생산실적관리(팝업 4개 포함)를 원본과 같게 동작시킨다.
- 기존 MSSQL과 기존 SP를 그대로 호출한다. DB 스키마나 SP는 바꾸지 않는다.
- 지금처럼 현장 PC에 설치하는 전체화면 프로그램으로 쓴다.

**비목표**
- 출하관리, 자재입고관리, 재고실사관리 화면
- 라벨·리포트 인쇄(`SP_CPOP303_PROD_RPT`, `SP_CPOP303_PRODLOT_RPT`, `F1soft.Framework.Report`). 버튼 자리만 두고 비활성으로 둔다.
- 새 디자인이나 사용성 개선
- 태블릿 모드(`_TabletPcFlag`)

**실패 기준** (돌아가더라도 실패로 본다)
- 원본과 다른 데이터가 DB에 저장된다(SP 인자 값·순서·형식이 다름).
- 원본에서 막히던 동작이 새 앱에서 통과되거나, 그 반대가 된다(아래 4장 버그 처리로 정한 것은 제외).
- 현장 PC 화면에서 배치가 어긋나거나, 글자가 잘리거나, 스크롤이 생긴다.
- 개발 중 운영 DB에 쓰기가 일어난다.

## 3. 제약

- 스택 **[사용자 결정]**: React + Vite(TypeScript) + Spring Boot + MyBatis + MSSQL + Material Design 3
- S_ERP 구조는 따르지 않는다 **[사용자 결정]**.
- DB: 개발과 테스트는 `iPlusERP_DEARYUNG_DEV`, 운영은 `iPlusERP_DAERYUNG` **[사용자 결정]**. 서버와 계정은 원본 `App.config`의 `SERVER_DB`와 같다.
  - 접속정보는 코드·문서·저장소에 넣지 않는다. 커밋하지 않는 로컬 설정 파일이나 환경변수로만 받는다.
  - 2026-11-13 확인: 인벤토리에 나오는 SP 18개(로그인 포함)가 DEV에 모두 있다.
- 기준 해상도 1920x1080. 원본처럼 창 폭 기준으로 확대하고 세로는 남는 만큼 늘려 화면을 꽉 채운다(시제품 `ScaledStage` 방식).
- 개발 PC: Java 21, Node 24, Maven 3.9. Spring Boot 4.1 + mybatis-spring-boot-starter 4.1을 쓴다 **[내 판단]** (2026-11 기준 최신 안정판).
- 현장 PC: 터치 화면이다 **[사용자 확인]**. Windows 버전은 모른다. **Windows 10 이상 64비트로 보고 진행한다 [내 판단].** 설치 단계(8장 9단계) 전에 실제 PC를 확인한다. Windows 7·8이나 32비트가 있으면 Electron 버전과 빌드 설정을 그때 조정한다.
  - 터치 기준으로 만든다. 마우스 오버에만 의존하는 동작은 두지 않고, 원본처럼 누름(눌림 색) 위주로 반응한다.
- 테스트 DB: 시험 데이터를 남겨도 된다 **[사용자 확인]**. 다른 사람과 함께 쓰는지는 신경 쓰지 않아도 된다.
- 버전 관리: 지금은 git을 쓰지 않고 로컬에서만 작업한다 **[사용자 결정]**. 마지막에 시작한다. 그때까지 단계별 되돌리기는 구현자가 폴더 백업 등으로 알아서 한다.

**로그인 관련 [사용자 결정]**
- `0000` 계정은 입력한 비밀번호를 무시하고 고정 비밀번호로 `SP_POP_LOGIN`을 호출한다. **동작은 유지**하고, 고정 비밀번호는 코드에서 빼서 서버 로컬 설정으로 옮긴다.

**출력 관련 [사용자 결정]**
- 헤더 [라벨출력] 버튼은 원본에서 [실적 등록]과 **같은 처리(저장 포함)** 를 하고 마지막에 인쇄한다. 저장까지는 원본대로 하고 **인쇄 단계만 생략**한다. LOT 팝업의 [라벨 출력] 버튼은 비활성으로 둔다.

**오류 표시 [내 판단]**
- 원본은 DB 오류가 나면 아무 알림 없이 빈 목록을 보여준다. 새 구조에는 네트워크와 서버가 하나 더 끼므로, 서버에 연결되지 않거나 서버 오류가 나면 원본과 같은 WARNING 알림창으로 "서버와 통신할 수 없습니다." 같은 문구를 띄운다. 서버를 재시작해 로그인 정보가 사라진 경우에는 "로그인 정보가 만료되었습니다. 다시 로그인하세요."를 띄우고 로그인 화면으로 돌아간다. 업무 검증 메시지는 원본 문구 그대로다.

## 5. 접근 방식

검토한 방식 세 가지:

| 방식 | 내용 | 득실 |
|---|---|---|
| **A. 기능 하나씩 끝까지 완성** | 로그인을 화면, 서버, DB, 설치형까지 실제로 동작시킨 뒤, 메인메뉴 → 생산 조회 → 버튼 → 팝업 순으로 하나씩 붙임 | 첫 단계부터 원본과 나란히 놓고 비교 가능. 초반에 화면 수가 천천히 늘어남 |
| B. 화면 전부 먼저 | 가짜 데이터로 화면을 전부 그리고 마지막에 연결 | 모양은 빨리 보이지만, 입력하면 줄줄이 다시 계산되는 동작은 실제 데이터 없이 맞추기 어려워 다시 고치게 됨 |
| C. 서버 전부 먼저 | SP 18개 API를 먼저 다 만들고 화면을 붙임 | 한참 동안 확인할 게 없고, 필요한 것은 화면을 만들며 드러남 |

**선택: A [사용자 결정].**

## 6. 전체 구조

```
[현장 PC]                                   [회사 서버 1대]                [DB 서버]
Electron 설치형 프로그램  ──HTTP(JSON)──>   Spring Boot API   ──JDBC──>   MSSQL
 └ React 화면 (빌드본 내장)                  └ MyBatis → 기존 SP/쿼리
 └ 기기별 설정 파일(로컬)
```

- 현장 PC **[사용자 결정]**: 설치형 전체화면 프로그램(Electron)
- 서버 **[사용자 결정]**: 회사에 1대를 두고 현장 PC들이 붙는다. 어느 PC에 둘지는 설치할 때 전산 담당자와 정한다. 코드는 서버 위치와 상관없이 같고, Electron 앱은 서버 주소를 설정 파일에서 읽는다.
- 개발 중 **[사용자 결정]**: 이 PC에서 서버와 화면을 같이 띄운다.

### 6-1. 저장소 구성 [내 판단]

```
MOKYANG_POP/
  frontend/   React + Vite + TS (시제품 위치를 그대로 쓰고 구조를 정리)
  backend/    Spring Boot 4 + MyBatis (Java 21, Maven — 이 PC에 Maven이 설치되어 있음)
  desktop/    Electron 껍데기 (frontend 빌드본을 띄움)
  docs/
```

git은 마지막에 시작한다(3장).

### 6-2. 백엔드 (Spring Boot + MyBatis)

- **API 형태 [내 판단]**: 화면 동작 단위의 REST JSON. SP 하나 또는 인라인 쿼리 하나에 엔드포인트 하나를 두는 것이 기본이다. 여러 SP를 순서대로 부르는 동작(준비 완료, 실적 등록, 공정 마감 등)도 **원본처럼 화면 쪽에서 순서대로 호출한다.**
  - 이유: 원본의 호출 순서와 중간 분기(`NextProdValidation` 등)를 그대로 옮기기 쉽고, 원본과 비교할 때 한 단계씩 맞춰볼 수 있다.
  - 대가: 원본처럼 트랜잭션이 없다. 원본도 SP를 하나씩 따로 커밋하므로 동작은 같다.
- **SP 호출**: MyBatis 매퍼 XML에서 `{call SP_xxx(#{a}, #{b}, ...)}`로 부른다. 인자 순서, 타입(VarChar/Int/Float), 날짜 형식(`yyyyMMddHHmmss`, `yyyyMMdd`)은 인벤토리 3장을 그대로 따른다. 원본에서 `'값'` 문자열로 넘기던 인자(T 방식)는 문자열로 바인딩한다.
- **인라인 쿼리**: 공정(`TPR102`), 작업장(`TPR102R`+`TPR101`, `'000001'` 고정), 설비(`TPR151`), 풀림방향(`TCO101` 157), 수주번호 변환(`TPR601LOT`/`TPR301R`), 재고 팝업 콤보(`TCO107`/`TCO108`)를 매퍼 XML에 원본 SQL 그대로 옮기고, 값만 `#{}`로 바인딩한다.
- **결과 매핑**: SP 결과 컬럼명을 그대로 받아 camelCase DTO로 매핑한다. 원본이 `.ToString()`으로 읽던 값의 형식(날짜 문자열, '1'/'0' 플래그)은 서버에서 바꾸지 않고 내려준다.
- **로그인과 사용자 정보 [내 판단]**:
  - `POST /api/auth/login`이 `SP_POP_LOGIN`을 호출한다. 성공하면 서버가 토큰을 발급하고, 그 안에 사번(`employee`)과 `factory_code`를 담는다.
  - 이후 요청은 토큰을 헤더로 보낸다. 서버는 토큰의 사번을 모든 IUD SP의 `@OPMAN_CODE`에, `factory_code`를 원본이 `Settings.factory_code`를 쓰던 자리에 넣는다. 원본이 `SelectedPlan.FactoryCode`를 쓰던 자리는 화면이 보낸 값을 쓴다.
  - 토큰은 화면 메모리에만 둔다. 프로그램을 다시 켜면 다시 로그인한다(원본도 항상 로그인 화면부터 시작).
  - 로그인 실패 시 "아이디와 패스워드를 확인하세요!"를 띄운다.
- **설정**: `application.yml`에는 자리만 둔다. 실제 DB 접속정보와 `0000` 비밀번호는 커밋하지 않는 `application-local.yml` 또는 환경변수로 받는다. 개발 기본 DB는 `iPlusERP_DEARYUNG_DEV`.
- **로그**: SP 이름, 인자, 소요시간을 서버 로그 파일에 남긴다. 원본의 SQL 로그를 대신한다.

### 6-3. 프론트엔드 (React)

- **시제품 처리**: `frontend/`의 시제품은 버리지 않는다. 화면 모양(`ScaledStage`, `theme.ts`의 원본 색상 토큰, 메인메뉴, 생산 화면 레이아웃 컴포넌트)을 가져다 쓰고, 폴더 구조와 상태 관리는 아래 기준으로 다시 잡는다.
- **MD3 [내 판단]**: MUI를 쓰고, MD3 토큰(색, 모양, 글꼴)을 테마로 정의한다. 단, **원본 색과 모양이 MD3보다 우선한다.** MD3는 원본에 없는 부분(포커스 표시, 눌림 효과 등)을 채울 때만 쓴다.
- **아이콘 [내 판단]**: 원본과 같은 Font Awesome 6 글리프를 쓴다(원본 `Assets/Fonts`의 otf 또는 같은 버전 웹폰트). 시제품의 MUI 아이콘은 교체한다.
- **화면 전환**: 로그인 → 메인메뉴 → 생산실적관리. 화면이 세 개뿐이라 라우터 없이 상태로 전환해도 되고, 라우터를 쓸지는 구현자 판단이다.
- **상태 관리**: 생산 화면 상태(검색 조건, 계획 목록, 선택 계획, `ProdData`, 자재1/2 목록, 작업시간)는 화면 단위 하나의 저장소(reducer 또는 작은 store)에 둔다. 원본 `ProductionModule`에 해당한다.
- **계산 로직**: `AutoCalcRatio`, `ChangeInputQty/GoodQty/RestQty/LossQty`(2급지 FIFO 포함), 잔량·LOSS 처리, `NextProdValidation`, `ProdStartValidation`, `ProdSaveValidation`은 **화면과 분리된 순수 함수**로 만들고 단위 테스트한다. 원본에서는 NumberPad 적용 → TextChanged 연쇄로 실행되던 순서를, 사용자 입력 하나가 들어오면 함수들을 원본과 같은 순서로 호출하는 방식으로 옮긴다(4장 #17·18).
- **숫자 형식**: NumberPad 결과는 원본처럼 정수(N0)로 반올림해 넣는다. 소수점 입력은 원본과 같게 사실상 동작하지 않는다(인벤토리 0장).
- **공통 컴포넌트**: 알림창(ShowAlertOk/YesNo, 700x450, "WARNING", "확인"/"예"/"아니요"), NumberPad(400x700, 1~9/0/00/./⌫/적용/취소, 제목·미리보기), 로그인 패드(`ShowLoginPad`, 원본 NumberPad 재사용), Combo 선택창(400x550), 달력(원본 `calendar_style`). 모달이 뜨면 원본처럼 뒤 화면에 흐림 효과를 준다.
- **팝업 4개**(재고 조회, LOT 생성, 작업일보, 생산일정): 별도 창이 아니라 앱 안의 대화상자로 띄운다. 크기는 원본 픽셀 크기(1920 기준)를 따른다. 생산일정의 최대화/원래크기 토글도 앱 안에서 재현한다.

### 6-4. 데스크톱 (Electron)

- 전체화면, 메뉴바 없음, 창 테두리 없음(원본 Release의 `WindowStyle=None`, Maximized).
- 중복 실행 방지: 이미 떠 있으면 새로 띄우지 않고 기존 창을 앞으로 가져온다.
- 최소화 버튼 → 창 최소화. 로그인 화면 닫기 → "프로그램을 종료하시겠습니까?" 확인 후 종료.
- **기기별 설정 [내 판단]**: 사용자 데이터 폴더의 JSON 파일 하나에 저장한다. 키는 원본 `Properties.Settings`와 같다(`id_save_check`, `employee_cache`, `device_work_*`, `device_workcenter_*`, `device_equip_*`, `device_worker_*`, 서버 주소). 화면은 공통 인터페이스로 읽고 쓴다. 브라우저로 개발할 때는 같은 인터페이스를 localStorage로 구현한다.
- **화상 키보드 [내 판단]**: 원본처럼 품목 검색과 참고사항 칸에 포커스가 가면 Windows 화상 키보드(TabTip)를 띄우고, 포커스가 빠지면 닫는다. Electron 메인 프로세스에서 실행한다. 수주번호 칸은 원본처럼 띄우지 않는다.
- **바코드**: 원본과 같은 키보드 웨지 방식이라 따로 처리할 것이 없다. "정확히 10자에서 조회, 이후 키 차단, 상태가 '1'이 아니면 전부 차단" 규칙은 화면에서 구현한다.
- **외부 URL**(작업의뢰서, 도면): 기본 브라우저로 연다. URL은 원본 그대로다(`_test` 포함).
- **자동 업데이트 [내 판단]**: 원본은 FTP에서 `POP.exe`를 받는다. 새 앱은 Electron 자동 업데이트를 쓰고, 업데이트 파일은 회사 서버(Spring Boot가 정적 파일로 제공하거나 사내 웹 경로)에 둔다. 설치 단계에서 구현한다.
- 설치 파일: Windows 설치 프로그램 하나(NSIS 등). 설치할 때 서버 주소를 설정 파일에 넣는다.
- **현장 전환 방식(설치 단계에서 결정)**: 아래 항목은 8장 9단계에 들어가기 전에 사용자, 전산 담당자와 정한다. 그 전 단계에는 영향이 없다.
  - 한 번에 바꿀지, 한동안 원본과 함께 쓸지
  - 원본 `user.config`의 기기 설정(공정, 작업장, 설비, 작업자, 저장 ID)을 옮길지
  - 원본 FTP 자동 업데이트를 어떻게 멈출지, 되돌리는 절차

## 8. 구현 순서 (방식 A)

각 단계가 끝나면 테스트 DB에서 원본 프로그램과 나란히 놓고 같은 조작을 해서 비교한다.

1. **기반**: backend 골격 + DEV 연결 확인(공정 001~005별 시험할 생산계획과 재고 LOT가 있는지 DEV만 조회해 확인. 없으면 사용자에게 알림), desktop 골격(전체화면, 중복 실행 방지, 설정 파일), frontend 구조 정리, 공통 알림창
2. **로그인**: 화면 + 로그인 패드 + `SP_POP_LOGIN` + 토큰 + 아이디 저장
3. **메인메뉴**: 로그아웃, 생산실적 진입
4. **생산 조회**: 헤더(공정/작업장 선택창, 수주번호, 날짜, 시계), 계획 목록, 선택 시 실적/자재/작업시간 조회, 작업참고사항, 접기/펼치기, 기기 설정 저장·복원
5. **실적 입력과 상태 버튼**: NumberPad, 계산 로직, 준비 시작 → 준비 완료 → 작업 중단/재시작 → 실적 등록(다음 실적/자동 마감) → 공정 마감, 설비·작업자 선택, 풀림방향
6. **자재투입 탭**: 바코드, [+]/[−], [투입], 위로/아래로
7. **팝업**: 재고 조회 → LOT 생성(004/005 실적 등록 경로) → 작업일보 → 생산일정
8. **보조메뉴 URL, 화상 키보드**
9. **설치와 자동 업데이트**: 설치 파일, 서버 주소 설정, 업데이트 경로

## 9. 시험 방법

- **계산 로직**: 순수 함수 단위 테스트. 원본 C# 코드의 분기마다 사례를 하나 이상 만든다(1급지/2급지 FIFO, 각 알림 조건).
- **SP 호출**: 백엔드 통합 테스트로 DEV DB의 조회 SP를 실제 호출해 컬럼 매핑을 확인한다. 쓰기 SP는 자동 테스트에서 부르지 않는다.
- **동작 비교**: 단계마다 같은 테스트 DB에서 원본과 새 앱을 각각 조작한 뒤 DB 결과(`TPR601` 실적, 자재, 작업시간 행)를 비교한다. 원본 프로그램을 DEV에 붙이려면 원본 `App.config`의 카탈로그만 바꾼 사본을 쓴다.
- **화면 비교**: 1920x1080, 1920x940, 1680x1050에서 원본 스크린샷과 겹쳐 본다.
- **운영 DB 보호**: 개발 설정에는 DEV 카탈로그만 둔다. 서버가 시작할 때 접속한 DB 이름을 로그에 찍는다.
